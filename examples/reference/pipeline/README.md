# The Pipeline reference app

The 0.13 reference app (release spec 0.13.0, decision D1; the §6 exit KPI): a multi-tenant
document-intake pipeline and its back office, built only through `id_effect_kit`. It is tier
`example` and `publish = false`. The name is the app's; `id_effect_resilience::Pipeline` is an
unrelated policy type, so the docs always say "the Pipeline reference app".

```rust
use pipeline::{Stage, stages};

let all = stages().block_on().into_result().unwrap();
assert_eq!(all.len(), 6);
assert_eq!(Stage::Ingest.next(), Some(Stage::Extract));
```

## What it does

| Stage | How | Battery (kit feature) |
|---|---|---|
| 1. Ingest | `Intake.ingest` (RPC mutation) or `POST /documents/upload` (the raw text kept in object storage); an `ExtractJob` is queued | `rpc`, `storage`, `jobs` |
| 2. Extract | structured output into a typed `Extracted` (decoded through its `Schema`, one repair retry, then the app's rules); the organization is enriched from an outside MCP tool server | `ai`, `mcp` (client) |
| 3. Classify | a bounded tool loop (4 steps, 8 tool calls, 30 s) with exactly two read-only tools of the tenant, `lookup_source` and `list_labels`; only the tenant's own labels attach | `ai` (tools, agent loop) |
| 4. Embed | the document's embedding against at most 200 earlier embeddings of the same tenant; the closest at cosine ≥ 0.97 is the duplicate | `embeddings` |
| 5. Review | the admin generated by `id-effect generate admin` (`/admin/<tenant>`) and the htmx review queue (`/review`), in English or German; see [Back office](#back-office) | `admin`, `audit`, `ui`, `i18n` |
| 6. Publish | `Intake.publish`; the document's `after_update` hook stages `DocumentPublished` in the outbox **in the update's transaction**; `Intake.status` (a subscription, as server-sent events) shows every change live | `repository` (hooks), `messaging`, `rpc-ws` |
| 7. Agents | one MCP server per tenant at `/mcp/<tenant>`: `search_documents`, `get_document` (described in the tenant's locale) | `mcp` |

**Data model.** `Source` 1:N `Document` N:M `Label` (through `document_labels`), `Document` 1:N
`Extraction`, all tenant-scoped (`#[entity(tenant = "tenant")]`), read with eager loading (one
`IN` query per relation, never one per row) and keyset pages (cursors stay stable while documents
arrive).

**Tenants.** `acme` (English) shares the main database with the job queue; `globex` (German) has
a database of its own, reached through a `TenantRouter`. The tenant of every request is the
`tenant` claim of its bearer token (the kit's `TenancyLayer` sets both the authorization tenant
and the SQL tenant from it); a tenant without a database has no connection at all.

## Secure by default

- Every route declares its access: `/health` and the htmx script are the only public routes;
  `/rpc` procedures each carry a guard (`editor` ingests, `reviewer` publishes, both read; a
  tenant claim is required); the upload route needs `editor`; the back office needs a
  `reviewer` or an `admin` of the tenant.
- Each MCP endpoint is guarded (an `agent` of that tenant), refuses browser origins outside
  `PIPELINE_MCP_ORIGINS` (none by default) and messages over 1 MiB, and exposes read-only tools.
- The model can call only the two registered tools; a tool a document talks it into calling is
  refused and fed back, never run (`pipeline_prompt_injection_cannot_call_unlisted_tool`). Every
  loop is bounded; prompts and completions are never logged.
- No live vendor call in CI (D8): `ScriptedModel` and the recorded OpenAI / Anthropic fixtures
  (`fixtures/*.json`) under wiremock.

## Back office

Stage 5: reviewers work in the admin and in the review queue, both under the app's
authentication and tenancy layers and behind `id_effect_axum`'s `SecurityLayer` (a masked CSRF
token on every `POST`, the nonce CSP, the security headers). Pages are maud (escaped by
default); htmx is the vendored, sha384-pinned script the app serves itself.

| Route | What | Who |
|---|---|---|
| `/admin/<tenant>` (`/source`, `/document`, `/label`, …) | the generated admin of the tenant: lists with search, filters and sorting, detail pages, forms, the label picker, bulk actions | `reviewer` or `admin` of that tenant, then a permission per page |
| `GET /review` | the queue: the tenant's documents in review (htmx reloads its table after a publication) | `reviewer` of the tenant |
| `GET`, `POST /review/{id}` | a document's panel (htmx swaps it in); accept it with a corrected title and publish it | `reviewer` of the tenant |
| `POST /review/locale` | the user's language | `reviewer` or `admin` of the tenant |

| Role | Admin permissions (`admin.<entity>.<action>`, `pipeline::admin::rbac`) |
|---|---|
| `reviewer` | `list` and `view` sources, documents and labels; `update` documents (the title, and the label picker: add or remove a tenant's label); `bulk` on documents (re-run extraction) |
| `admin` | everything the admins offer (documents are never created in the admin: they arrive through ingestion) |

Each tenant has its own site, `/admin/<tenant>`, reading that tenant's database through the
tenant router (`TenantRouter::for_tenant`) and its rows only (`CurrentTenant`); its guard admits a
principal of that tenant only. Every create, update, delete, label change and bulk action is
appended to the hash-chained audit log (`audit_log`, created by `pipeline::migrate` in every
tenant database) in the change's own transaction. The bulk action **Re-run extraction** sets the
documents back to `ingested` (audited with the action) and queues their `ExtractJob`s to run
2 seconds later (`admin::document::RERUN_DELAY`): the jobs live in the main database, the
documents in the tenant's, so the jobs wait for the action to commit. `COOKIE_KEY` (base64, at
least 64 bytes) signs the CSRF cookie so every instance accepts the others' sessions; without it
a key is generated at startup.

**Generated, then edited.** `src/admin/` was produced with:

```bash
cargo run -p id_effect_tool --bin id-effect -- generate admin Source --path examples/reference/pipeline
cargo run -p id_effect_tool --bin id-effect -- generate admin Document --path examples/reference/pipeline
cargo run -p id_effect_tool --bin id-effect -- generate admin Label --path examples/reference/pipeline
```

They wrote `src/admin/{mod,source,document,label}.rs` and `pub mod admin;` in `src/lib.rs`. Every
edit made after generation (the CI job `reference-pipeline` regenerates into a scratch copy and
prints the difference):

1. `Cargo.toml`: id_effect_kit's `admin` feature (the generator's "Do by hand" line), `audit`
   (the audit log) and `ui` (the review queue), and `maud = "=0.27.0"` (`html!` names it).
2. All four files: formatted with the workspace's rustfmt settings (two-space indent).
3. `mod.rs`: `site` and `router` take the app and the tenant (the document admin's bulk action
   needs both); added `ROLE_ADMIN`, `tenant_prefix`, `reviewer_may`, `rbac` (the roles above),
   `guard` (the role and the tenant claim), `tenant_site` (prefix `/admin/<tenant>`, the policy
   over `rbac`, labels from `ui::catalog`) and `routes` (every tenant's site on its own
   database); a test of the grants and one of the per-tenant prefixes; `test_app` for the tests.
4. `source.rs`: search over `name` and `url` only; `trust` filtered by its two values.
5. `document.rs`: `ACTIONS` without `Create`; the list without `body`, sortable by `id`,
   `title` and `status`, newest first; `status` filtered by the pipeline's statuses; the bulk
   action `rerun_extraction`; `register` takes the app and the tenant; the configuration test
   follows the new list.
6. `label.rs`: documentation only.
7. Each module's `every_page_is_behind_the_guard` test calls `router` with the test app and a
   tenant.

| Test | Shows |
|---|---|
| `pipeline_admin_crud_and_audit` | create, update, delete in the admin, each in the tenant's audit chain; globex's admin writes to globex's database |
| `pipeline_admin_denied_without_role` | 401 anonymous; 403 for an editor, another tenant's reviewer, an admin without a tenant; a reviewer cannot create or delete |

## Locales

The back office speaks English (the default) and German. Its messages are
`locales/en/backoffice.ftl` and `locales/de/backoffice.ftl` (Project Fluent), embedded in the
binary by `pipeline::ui::catalog`, together with id_effect_i18n's translations of the `Schema`
validation messages (`schema-*`). The catalog is built with `require_complete`: a German message
missing for an English one fails at startup (and in `ui::tests`).

| Messages | Used by |
|---|---|
| `nav-*`, `review-*`, `status-*`, `locale-*`, `backoffice` | the review queue (`src/ui/`) |
| `admin` and its attributes | the admin's page text (`id_effect_admin::labels::UI_MESSAGES`) |
| `pipeline.<entity>`, `<entity>.<field>` | the admin's entity and field labels (`#[entity(label = …)]`) |
| `backoffice.rerun-extraction` | the bulk action's label |

Each request's locale is, in order: the signed-in user's own choice (`POST /review/locale`, kept
per `<tenant>/<user>` by `ui::LocalePreferences`, at most 10 000 users), the best match of
`Accept-Language` (bounded parse), then English. Only `en` and `de` can be chosen (no path or
file is ever built from the request). Responses carry `Content-Language` and `Vary`, message
arguments are escaped by maud and wrapped in Unicode bidi isolation marks. The extraction
labels and the MCP tool descriptions (`ai::messages`) follow the tenant's locale, not the
reader's. To add a locale, add `locales/<tag>/backoffice.ftl` with every message, embed it in
`ui::catalog`, and list the tag in `ui::LOCALES`.
