# ADR 0015 — Breadth batteries

## Status

Accepted (owner decision D16, 2026-10-21; the defaults of D1–D15 as written). Proposed
2026-10-21. Release 0.13.0 "Breadth", track T9 with E1.3, E3.3 part 2 and E5.5, leaf
`r13-t0-adr0015`; acceptance recorded in [0.13.0 D16](../../.maestro/specs/releases/0.13.0.md) and
PLAN-OF-PLANS §11. The 0.13.0 exit gate needs every rule's enforcement point green at the tag. One
later owner decision amends a number here: the eager-loading pair limit of §15 is 0.45, not 0.25
(2026-10-24, follow-up F66). The decisions come from the release spec's "Owner
decisions" table (D1–D15) and its "Security — ADR 0013 applied to the breadth batteries" table.
Where those disagree with PLAN-OF-PLANS, PLAN-OF-PLANS wins; where this ADR adds a fact the release
spec could not know (the MCP revision current on 2026-10-21, the measured 0.12.0 baseline), this
ADR records it and the leaf that owns the code follows it.

Owner decisions already taken (not re-asked): everything buildable ships before 1.0 (L15); UI is
integrated, not built (L7); batteries are effect-native and built on proven Rust crates (L2);
reference apps are the consumers (L4); no JavaScript toolchain in the repository (L12); GraphQL is a
non-goal; the six breadth row targets moved from 0.12.0 to 0.13.0 with their values unchanged (0.12
D1, ADR 0014 §15). The nine open questions of the release spec are recorded at the end with the
defaults this ADR takes; the owner can overturn any of them before accepting it.

RT 85.9 (#1) with 7 red rows. Four of the red rows are breadth the platform does not ship at all:

| Row | 0.12.0 | What exists |

| `data.orm` | 63 | `Repository<T>`, `#[derive(Entity)]`, global soft-delete/tenant filters, offset pages. No relations, no eager loading, no lifecycle hooks, no keyset pages. |

PLAN-OF-PLANS §6 names a "Pipeline reference app" as the 0.13 exit KPI but never defines it. Every
row above needs a consumer at production level (L4), and every new surface (an admin, server
rendered views, a model that calls tools, an MCP endpoint, a locale header, a page cursor, a tenant
from a request) is an attack surface that ADR 0013 must cover from its first commit. This ADR fixes
the shape of each battery, the app that proves them, and the rule each surface obeys.

## Decision

### 1. The Pipeline reference app (D1)

**Pipeline** (`examples/reference/pipeline`, package `pipeline`, tier `example`, `publish = false`,
built only through `id_effect_kit`) is a multi-tenant document-intake pipeline and its back office:

1. **Ingest:** documents arrive by RPC mutation or upload (storage) for a tenant; one job per stage
   (`id_effect_jobs`).
2. **Extract:** a model turns text into a typed `Extraction` (structured output decoded through
   `Schema`, `ai.llm#4`).
3. **Classify:** a bounded tool loop calls `lookup_source` and `list_labels` (typed tools, `#3`,
   `#8`) and attaches `Label`s.
4. **Embed:** embeddings (`#5`) flag near-duplicates within the tenant over a bounded candidate set.
5. **Review:** reviewers work in the admin generated by `id-effect generate admin` (`web.admin`) and
   in an htmx + maud review queue (`web.ui`), in English or German (`eco.i18n`: Accept-Language plus
   a per-user override).
6. **Publish:** an `after_update` lifecycle hook (`data.orm#7`) writes `DocumentPublished` to the
   outbox in the same transaction; an RPC subscription shows live status.
7. **Agents:** an MCP server exposes `search_documents` / `get_document` to outside agents (guarded,
   Origin-checked); an MCP client enriches documents from a fixture MCP tool server (`#6`).

Data model: `Source` 1:N `Document` N:M `Label` (join table `document_labels`), `Document` 1:N
`Extraction`, all tenant-scoped. Tenant `acme` (locale `en`) shares the main database; tenant
`globex` (locale `de`) is routed to its own database (`eco.tenancy#8`, margin). AI in CI is
deterministic (§8). The exit KPI: CI job `reference-pipeline` green on Postgres with both tenants,
both locales, the admin, MCP server and client, and a clean prod posture with zero accepted risks.

The app is built by two leaves (`r13-w6-pipeline` core, `r13-w7-pipeline-backoffice`) split by
directory, so each agent's context stays bounded. The name collides with
`id_effect_resilience::Pipeline` (a policy type); the book and README always say "the Pipeline
reference app". It is the smallest app that exercises all six rows at production level: an
admin-only app would leave `ai.llm` and `eco.tenancy#8` unproven, a chat app would leave
`web.admin` and `data.orm#7` unproven.

### 2. Crate placement (D2, D3, D5, D6)

| Battery | Where | Tier at entry | Depends on |
|---|---|---|---|
| Admin (D2) | new crate `crates/id_effect_admin` | integration | axum `ui`, sql `repository`/`audit`, authz; optional i18n |
| Server-rendered UI (D3) | `id_effect_axum` feature `ui` (no new crate) | integration (axum's) | `maud` (exact pin), the vendored htmx file |
| i18n (D5) | new crate `crates/id_effect_i18n` | integration | `fluent-bundle`, `fluent-langneg`, `intl_pluralrules` (exact pins); optional axum, maud, Schema |

| Leptos (D4) | recipe `examples/recipes/leptos-ssr`, outside the workspace | example | — |

- Each new crate moves to tier `platform` when the Pipeline depends on it (ADR 0010 check P), which
  the 0.13.0 exit gate requires for all three. ADR 0010 Amendment 9 (leaf `r13-t0-skeletons`) admits
  them; `scripts/validate-crate-packaging.sh` publishes them in dependency order: i18n after
  core/axum, ai after platform/config, admin after sql/axum/authz/i18n, all three before kit and
  tool.
- The admin is a crate, not generated code only: generated code cannot reach "documented" (no
  published, tested crate to point at), and `id_effect_axum` must not depend on `id_effect_sql`.
  `id-effect generate admin <Entity>` writes a registration module against the crate's API
  (`AdminSite::register::<E>()`).
- New kit features `ai`, `mcp`, `embeddings`, `admin`, `ui`, `i18n`, `tenancy` are in `full` and
  **off by default**, so the `service` template's K1/K2/K6 do not move; the K6 cold-build delta of
  each is reported at exit.

### 3. Server-rendered UI (D3)

`id_effect_axum` feature `ui`: maud `Markup` as a typed route response; `Component` (a props struct
plus slot children); `Layout` and partials, choosing fragment or full page by `HX-Request`; htmx
helpers (`HxRequest`, `HxTrigger`, a same-origin-only `HxRedirect`); form helpers bound to `Schema`
errors (margin, `web.ui#5`).

- maud is chosen over minijinja because templates are compiled and type-checked with the handler,
  and escaping is the default rather than a configuration. Raw HTML is reachable only through
  `ui::trusted_html`, a reviewed allowlist module; a grep test keeps `PreEscaped` out of every other
  file of `crates/id_effect_{axum,admin}/src`.
- **htmx 2.0.x is one vendored, hash-pinned file** (`crates/id_effect_axum/assets/`), served from the
  app's own origin, its sha384 and 0BSD license recorded in `assets/README.md` and checked by
  `htmx_asset_hash_matches_readme`. No CDN, no bundler, no npm (L12 spirit). The served page's CSP
  is `script-src 'self'`; htmx runs with `htmx.config.allowEval = false` and
  `htmx.config.selfRequestsOnly = true`. Updating the file is a reviewed leaf.
- Server-driven interactive views (`web.ui#3`) and an asset pipeline (`#4`) remain non-goals (L7).

### 4. Leptos is a recipe (D4)

`examples/recipes/leptos-ssr` (outside the workspace, its own lockfile, like `labs/`) shows Leptos
SSR with hydration served by the id_effect axum host and calling an id_effect RPC service, with a
pinned Leptos and no npm (cargo-leptos or the wasm target only). It has its own CI job
`recipe-leptos` and a book chapter. `web.ui#7` (a first-class component framework) is not counted;
a first-party Leptos or Dioxus crate stays a 1.x ecosystem lever (PLAN-OF-PLANS §9). The recipe is
first in the scope-cut order.

### 5. i18n over Project Fluent (D5)

`id_effect_i18n` wraps Fluent rather than gettext (no CLDR plural selectors in the message format,
`.po` tooling outside Rust) or ICU4X MessageFormat (MF2 tooling still young). Fluent gives CLDR
plurals through `intl_pluralrules`, and `fluent-langneg` does negotiation. 0.13 scope:

- `#1` a `Catalog` of Fluent resources per locale, loaded from an allowlisted directory or embedded,
  with a missing-key fallback chain and a startup check that every locale has every key of the
  default locale;
- `#2` CLDR plurals through Fluent selectors;
- `#3` Accept-Language negotiation with a cookie or per-user override, bounded parsing and a locale
  allowlist;
- `#5` translated `Schema` validation messages (error codes from `schema/parse_errors.rs` map to
  message ids; `en` and `de` ship);
- `#7` a `Locale` capability (`CurrentLocale` in the environment) with `with_locale` switching per
  request or fiber;
- `web.ui#8`: `maud::Render` for messages, arguments escaped, Unicode bidi isolation on.

Locale-aware number/date/currency formatting (`#4`), extraction tooling (`#6`) and localized routes
(`#8`) are 0.15 (E13.3).

### 6. The AI crate (D6)

`id_effect_ai` leaves `labs/` as one crate with features `openai`, `anthropic`, `ollama`, `cursor`,
`tools`, `embeddings`, `mcp`, `mcp-http`, `test-util`. Chat: OpenAI and Anthropic. Embeddings: OpenAI
and Ollama. The labs Cursor agents module stays behind the non-default `cursor` feature with its
fixture tests (no API loss; Open question 3). Module layout: `chat`, `stream`,
`vendors/{openai,anthropic,ollama}/{mod,chat,embed}.rs`, `tools/`, `embeddings/`, `mcp/`, `testing`.

- **All HTTP goes through `id_effect_platform`'s client**, so the 0.11 SSRF policy, body caps,
  redirects off and timeouts apply to every provider base URL and every MCP client connection. No
  adapter builds its own `reqwest::Client`.
- API keys are `id_effect_config::Secret`. Prompts and completions are never logged unless
  `dangerous_log_prompts()` is taken (recorded). `max_tokens` has a finite default; requests have a
  timeout; responses and streams have byte caps.
- `#4` structured output decodes through `Schema` (refinements run); a decode failure is a typed
  error with one bounded repair retry. `#3` a `Tool` has `HasSchema` input and output, exported as
  JSON Schema by `schema/json_schema_export.rs`, and maps to both vendors' tool-call formats. `#8`
  `ToolLoop` runs under the §9 budgets.

### 7. MCP: an own implementation pinned to one revision (D7)

`id_effect_ai::mcp` is an effect-native MCP server and client (tools, resources, prompts,
cancellation; stdio and Streamable HTTP), not a wrapper around the `rmcp` SDK: tools are the same
`Tool` values the agent loop uses, the HTTP endpoint is an `id_effect_axum` route with a typed
`.guard(g)`, and the client is the platform client. `rmcp` is a **dev-dependency only**, the interop
peer in tests in both directions (`mcp_interop_rmcp_client_against_our_server`,
`mcp_interop_our_client_against_rmcp_server`).

**Pinned revision: `2026-07-28`**, the current stable MCP specification revision on 2026-10-21 (the
release spec's floor is 2025-06-18). `rmcp` 3.x speaks it, so the interop peer is an `rmcp` 3.x
release, exact-pinned by `r13-e9-1-mcp`. The revision is stateless, and that shapes the
implementation:

- There is no `initialize` handshake and no protocol-level session (`Mcp-Session-Id` is gone). Each
  request carries its protocol version and client capabilities in `_meta`; the server implements
  `server/discover`; a request for any other revision is answered with
  `UnsupportedProtocolVersionError`. Interop with clients that only speak 2025-11-25 or older is not
  in 0.13 (a compatibility path is a later, additive change).
- Server-to-client change notifications use `subscriptions/listen`; request-scoped notifications
  (progress) flow on the request's own response stream. Cancellation interrupts the handler fiber
  and runs its finalizers: on Streamable HTTP the client closing the response stream is the
  cancellation signal; on stdio it is `notifications/cancelled`.
- Streamable HTTP POSTs carry `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name`; the server
  answers a request whose headers disagree with its JSON-RPC body with `400` and `HeaderMismatch`,
  so routing done by intermediaries on the headers cannot be steered by a different body. The
  client mirrors `x-mcp-header` tool parameters into `Mcp-Param-*` headers, validating names and
  values as B23 requires of the generated RPC clients.
- Server-initiated input (sampling, elicitation, roots through multi round-trip requests) and the
  tasks extension are not offered in 0.13; the client advertises none of them.
- The release spec's "session ids bound to the principal" rule applies to what replaces sessions:
  **every identifier the server mints and later accepts back** (a handle passed as a tool argument
  for cross-call state) is 128-bit random and bound to the authenticated principal, and one
  presented by another principal is refused; a `subscriptions/listen` stream carries only
  notifications about resources its principal may read. The test keeps its
  name, `mcp_session_bound_to_principal`, because the Security table and `surface_013.rs` look it up
  by name.

If a newer revision becomes current before `r13-e9-1-mcp` starts, that leaf re-pins this section (one
line here and a row in PLAN-OF-PLANS §11) before writing code; it never pins a draft revision. Open
question 4 lets the owner switch to wrapping `rmcp` instead.

### 8. Deterministic AI in CI (D8)

No PR or push job calls a live AI vendor, and no API key exists in CI. Vendor adapters are tested
against wiremock fixtures recorded from the vendors' documented examples (each fixture cites its
source page); the Pipeline and the agent loop run on `id_effect_ai::testing::ScriptedModel`, labelled
as scripted in the book and the README. An optional `workflow_dispatch` smoke with repository
secrets may exist; it is never a required check.

### 9. Tool safety (D9)

A model has no authority of its own; the library bounds what it can make the program do:

- A model can call only tools registered on the call's `ToolSet`. An unknown name is answered with a
  typed refusal fed back to the model and is **never executed**.
- Arguments are decoded through the tool's `Schema` (refinements included) before the handler runs;
  a decode failure is fed back as a typed error.
- Default budgets per loop: **8 steps, 32 tool calls, 60 s**; tool output is capped at **64 KiB**
  before it re-enters the context. Every limit is configurable and none can be infinite.
- A tool that writes declares `effects = write` and runs only under an explicit
  `ToolPolicy::allow_writes`. Granting it to a set that is exposed over MCP is recorded in the
  posture registry (`dangerous_mcp_write_tools`).

Prompt injection is not solvable by a library; bounded authority is the library's part, and
THREAT-MODEL.md states the residual risk. The Pipeline test
`pipeline_prompt_injection_cannot_call_unlisted_tool` feeds a hostile document through the loop.

### 10. Tenant resolution (D10)

- The tenant comes from the authenticated principal's tenant claim (`id_effect_authz::Tenanted`) by
  default. Host-based resolution works only through a configured allowlist (a Host outside it has
  no tenant). Header-based resolution exists only as `dangerous_tenant_from_header()`, recorded,
  even behind a trusted gateway (Open question 7).
- One `TenantResolver` feeds both `id_effect_authz::TenantScope` and `id_effect_sql::CurrentTenant`
  through kit feature `tenancy`, so authorization and queries can never disagree about the tenant.
- `TenantRouter` (`eco.tenancy#8`) is an `SqlClient` mapping tenant → pool, a bounded LRU (default
  64 pools) that composes with `RoutingSqlClient` replicas. An unknown tenant has no connection: it
  fails closed, it never falls back to the shared database.

### 11. Keyset cursor format (D11)

`find_after(PageCursor)` returns `Paged<T> { items, next, prev }` over the primary key and the
declared sort columns, stable under concurrent inserts; offset `Page` stays. The cursor is opaque
base64url of the sort-key tuple plus a fingerprint of the filter set, at most 1 KiB, decoded through
a bounded `Schema` (`PageCursor::decode`, fuzzed as `sql_page_cursor`). It is **not signed**: every
query re-applies the tenant and access scope, so a forged cursor only moves within the caller's own
rows (`tampered_cursor_stays_in_scope`), and an HMAC key would add rotation and secret handling for
no isolation gain. A cursor whose fingerprint differs from the request's filters is refused. Page
size defaults to 50 and is capped at 500.

### 12. Lifecycle hooks run inside the transaction (D12)

`EntityHooks` (`before_insert`, `after_insert`, `before_update`, `after_update`, `before_delete`,
`after_delete`) run inside the write's transaction, in that order; a failing hook rolls the write
back. Callbacks after commit would make "write + event" non-atomic; events-only hooks could not
veto a write. The optional `outbox` adapter (sql feature `outbox`) writes an event through
`id_effect_messaging` in the same transaction, which is how the Pipeline publishes
`DocumentPublished`.

### 13. Stored targets unchanged (D13)

The stored 0.13.0 row targets in `docs/scorecard/scorecard.json` stay as moved by 0.12 D1:
`data.orm` 88, `web.ui` 67, `web.admin` 50, `ai.llm` 75, `eco.i18n` 63, `eco.tenancy` 75, plus the
`sec.supply` 100 carry-over from 0.12.0. Margins are reported, not targeted. This leaf does not edit
`scorecard.json`; it restates PLAN-OF-PLANS §6 and the release spec's `scorecard:` block on the
measured 0.12.0 baseline (§17).

### 14. `any_env` (D14)

`impl<A, E> Effect<A, E, ()> { pub fn any_env<R>(self) -> Effect<A, E, R> }` in `kernel/effect.rs`
beside `widen`, plus the `LocalEffect` twin: an environment-free effect runs under any environment
without a closure or boxing beyond the existing representation (F52). It lets the F27 generated
client batcher drop its per-caller-environment resolver table. The name is Open question 6.

### 15. Bench budgets: measure first (D15)

The eager-loading pair gate `orm/eager_100x10 / orm/n_plus_one_100x10 ≤ 0.25` (owner decision
2026-10-24: **0.45**, measured 0.313–0.416; follow-up F66 brings it back toward 0.25) is written now: it is a
ratio of two measurements of the same stack (SQLite in memory). `i18n/format_plural` and
`ui/render_list_50` start as `report` gates; `r13-e-benches` writes their budgets after measuring,
and the owner confirms them at exit (as 0.12 D5). Every 0.12 gate (secure-stack delta ≤ 5 µs, unary
RPC delta ≤ 3 µs, batch pair, h3/h2 pair) is unchanged.

## Consequences

Positive:

- Six rows leave red or move up with one consumer that proves them together, so the exit re-score
  can cite one CI job (`reference-pipeline`) for production level on all six.
- Every battery inherits ADR 0013 from its first commit: the admin cannot be mounted without a
  guard, a model cannot call a tool that was not handed to it, a forged cursor stays inside the
  caller's rows, and a tenant never comes from a header without a recorded opt-out.
- The UI, i18n and admin stack is all Rust, compile-checked and escaped by default, with one
  hash-pinned JavaScript file and no toolchain (L12).
- AI evidence is reproducible: no secret in CI, no flaky vendor, and the same `Tool` values serve
  the agent loop and the MCP server.

Negative:

- Three new crates (`id_effect_admin`, `id_effect_i18n`, `id_effect_ai`) for the 0.18 crate review
  (E10.3) to justify, and three crates.io names to set up (D17).
- maud and Fluent are pre-1.0 and exact-pinned; every bump is work. htmx is a vendored supply-chain
  item outside `cargo deny`, kept honest by its hash test and a reviewed update leaf.
- An own MCP implementation tracks a moving specification. The pinned 2026-07-28 revision is
  stateless and does not interoperate with clients that only speak 2025-11-25 or older until a
  compatibility path is added.
- Wiremock fixtures prove the adapters against documented examples, not against today's vendor
  behaviour; an assessor may weigh that (release spec Risk 4).
- The keyset cursor is unsigned by design; it reveals the sort-key values of a row the caller could
  already read, and nothing more.
- Kit features stay off by default, so the `service` template does not show the breadth batteries
  until a user turns them on.

## Alternatives considered

- **A data pipeline without a back office, an admin-only app, or a chat/agent app as the Pipeline
  (D1).** Rejected: each leaves at least one of the six rows without a production consumer.
- **Admin as generated code only, or as an `id_effect_axum` feature (D2).** Rejected: generated code
  has no published, tested crate to cite ("documented" unreachable), and axum must not depend on sql.
- **minijinja for views, or a new `id_effect_ui` crate (D3).** minijinja is runtime-checked and
  escapes by configuration; a new crate adds a review burden for what is a feature of the HTTP host.
- **A first-party Leptos crate (D4).** Rejected for 0.13 (L7, §9 lever): a recipe proves the
  integration without freezing an API on a fast-moving framework.
- **gettext or ICU4X MessageFormat for i18n (D5).** gettext lacks CLDR plural selectors in the
  message format and brings non-Rust tooling; ICU4X MF2 tooling is not yet mature. Fluent is listed
  in L2.
- **Dropping the Cursor agents module, or splitting the AI crate (D6).** Rejected: no API loss for
  labs users, and the feature gate keeps it out of default builds (Open question 3).
- **Wrapping `rmcp` (D7).** Rejected by default: the server must use the axum host's guard
  typestate and the platform client's SSRF policy, and tools must be the agent loop's `Tool`
  values; adapting `rmcp`'s own transport and tool model to both is more code than the protocol
  surface 0.13 needs. Open question 4 keeps it available.
- **Pinning MCP 2025-06-18 or 2025-11-25.** Rejected: 2026-07-28 is the current stable revision and
  removes sessions, so pinning an older one would ship a stateful design the specification has
  already left, and its interop peer (`rmcp` 2.x) is no longer current.
- **Live vendor calls in CI (D8).** Rejected: secrets in CI, cost and flakiness, and no PR from a fork
  could run them.
- **Tools callable by name (D9).** Rejected: a prompt-injected model could reach any handler in the
  process.
- **Tenant from a header by default (D10).** Rejected: any client can set a header; a gateway that
  sets it must be trusted explicitly, and that choice is recorded.
- **An HMAC-signed cursor (D11).** Rejected: the scope re-check already confines a forged cursor, and
  a signing key adds rotation and secret handling for no isolation gain.
- **Hooks after commit, or events only (D12).** Rejected: after-commit loses atomicity between the
  write and its event; events alone cannot veto a write.
- **Raising the stored targets to the margins (D13).** Rejected: margins are a buffer for the gate,
  not a commitment (Open question 9).
- **Writing the i18n and UI budgets now (D15).** Rejected: a budget written before the first
  measurement measures the guess, as the 0.11 secure-stack ratio did.
