id_effect Platform Scorecard

Each cell scores how well that framework handles that capability out of the box, on a 1–100 scale. 100 means best in class for an enterprise team today. The id_effect column comes from an audit of this repository's source, tests, CI and docs at each release tag; the other columns are expert assessments of each framework's first-party stack and its de facto standard libraries, frozen as a dated snapshot. Each id_effect score is capped by maturity: labs-only work cannot score above 39, and 80 or more requires a published crate with docs, an example and integration tests. The rules are in docs/scorecard/METHOD.md and the data in docs/scorecard/scorecard.json. This page is generated by scripts/scorecard.sh --html, which also computes every index shown here; scripts/scorecard.sh --self-test checks them.

      How to read this

      Scope of each column

        Scale

        • 90–100: best in class; first-party, mature, and what enterprises standardise on.
        • 70–89: strong, with minor gaps or a third-party standard.
        • 40–69: partial, DIY wiring needed, or immature.
        • 10–39: primitives only, labs or stub quality.
        • 1–9: absent.

        Caveats

        • Every score is a judgment call. id_effect's are traced to files in this repo (the evidence under each capability is the latest one). The other columns are a dated snapshot and have not been checked line by line.
        • The unweighted index weights every row equally. The runtime index weights core model, concurrency, fault tolerance and distribution more heavily, and id_effect closes much of the gap under that weighting.
        • Target versions show planned scores, not measurements. A drop of 5 or more between measured versions needs an ADR note, shown under the row.
        • Rows are biased toward application-framework features, because the stated goal is a batteries-included corporate stack.
