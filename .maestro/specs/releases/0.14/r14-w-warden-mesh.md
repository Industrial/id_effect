# r14-w-warden-mesh

Leaf of `.maestro/specs/releases/0.14.0.md`, section "E13.2 — Promote (19 rows) and Warden". The
release spec's row is binding; this file exists so Maestro can track the leaf as its own task.

Wave 4, critical path. Blocked by: r14-w-warden-core (W3), r14-s-nats (W1; the `MessageBroker` on
NATS and a NATS test container with TLS), r14-s-parallel-supervision (W2; significant children and
`max_children`), r14-s-core-runtime (W1; core.race#8 and conc.coordination#8 must be met for the rows to
reach 100 — without it this leaf still promotes the level). Blocks r14-w-warden-ops (W5) and
r14-x-level-audit. Never cut. Runs beside r14-p-ledger, r14-p-relay and r14-e-fuzz-security, none of
which touches `examples/reference/warden/**` or the `reference-warden` job. Toolchain commands run as
`devenv shell -- <cmd>`.

Defaults taken (owner may overturn): placement by rendezvous hash in the app (`src/placement.rs`) —
the node crate has load-based placement (`place`, crates/id_effect_node/src/placement.rs:187) but no
key-based sharding (dist.placement#6 is open and slotted for 0.16), so `on_membership` re-placement
picks the next owner by key, not by load; dist.membership #3/#4 are exercised by a discovery-chain test
rather than by running inside Kubernetes. This is the largest Warden leaf (5 test files, ~38 tests);
if it does not fit one wave, split `tests/coordination.rs` + `tests/race.rs` + `src/{coordination,deadline}.rs`
into a sibling leaf `r14-w-warden-concurrency` (same wave, disjoint files).
