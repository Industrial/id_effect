# r14-p-ledger

Leaf of `.maestro/specs/releases/0.14.0.md`, section "E13.2 Promote". The release spec's row is
binding; this file exists so Maestro can track the leaf as its own task.

Wave 4. Blocked by: r14-s-data-fp (Validation, NonEmpty), r14-s-testing (seeded test order),
r14-s-parallel-supervision (pool metrics), and every W2–W3 leaf that edits Ledger files (rebase, not
shared ownership; r14-f-idempotency-pg's `src/idempotency.rs` is not owned here). Runs beside
r14-p-relay, r14-e-fuzz-security and r14-w-warden-mesh (disjoint: only the `reference-ledger` job of
ci.yml). Blocks r14-p-toolchain (which takes the Ledger's `main.rs` and lint fixes after this leaf)
and r14-x-level-audit.

Defaults the owner may overturn: the parallel workload is the statement build (the Ledger's only
CPU-bound batch path), not the audit-chain check (that lives in id_effect_audit, which this leaf
does not edit); id_effect_fp (where r14-s-data-fp puts `Validation` and `NonEmpty`),
id_effect_optics and id_effect_test's `order` feature are named directly in the Ledger manifest, as
`id_effect` already is: none is reachable through the kit at HEAD, and this leaf never edits
crates/id_effect_kit/Cargo.toml (an `fp` kit feature is a 0.15 tidy-up); the seeded-order target
covers the Ledger's in-process tests only, since the container-backed ones keep their per-test
isolated databases under nextest; the wire shape of every schema is kept so
the RPC contract check against v0.13.0 stays additive-only.
