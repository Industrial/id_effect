# r14-s-nats

Leaf of `.maestro/specs/releases/0.14.0.md`, section "E13.1 Sweep" (added by owner decision D11,
2026-11-03). The release spec's row is binding; this file exists so Maestro can track the leaf as its
own task.

Wave 1, critical path (skeletons → nats → warden-core → warden-mesh). Blocked by: r14-t0-skeletons
(crate skeleton, Amendment 10, ci.yml `-p` line, kit feature `nats`). Blocks r14-w-warden-mesh (NATS
intake), r14-e-fuzz-security (`nats_message_headers`) and r14-e-benches (broker throughput). Never cut.
Runs beside r14-s-kafka and r14-s-amqp: never edits `crates/id_effect_test/src/containers/spec.rs`
(r14-s-kafka owns it); the three share only the append-only module lines in id_effect_test.

Defaults the owner may overturn: JetStream rather than core NATS (core NATS has no ack, redelivery or
durable groups, so it cannot implement `MessageBroker`); one stream per topic (not one stream with a
subject per topic); dead-lettering done by the client with our headers (same DLQ shape as Redis, Kafka
and AMQP) instead of the server's max-deliveries advisory; streams created on first use. Not done here:
KV and object store, NATS services/request-reply, leaf nodes and superclusters, a shared broker
conformance suite in id_effect_messaging.
